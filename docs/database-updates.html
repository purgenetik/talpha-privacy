Nuclear Database Update System

Purpose

NuclideDatabaseUpdater.kt keeps nuclear data independent from the Android application release cycle.

The application can therefore use a newer database without requiring a new APK/AAB, as long as the database remains compatible with the reader.

Startup flow

At startup, MainActivity executes database loading on Dispatchers.IO:

loadBestAvailableDatabase(context)

The updater performs:

read latest local version
        ↓
download remote manifest
        ↓
compare remote and local version
        ↓
if remote > local:
    download candidate database
    parse candidate
    validate version
    install candidate
        ↓
load latest local database

Manifest

The updater downloads a small JSON manifest from a configured Google Drive file ID.

The manifest contains:

latestVersion
fileName
fileID

The code requires:

latestVersion > 0
fileName is not blank
fileID is not blank

Version comparison

A download is attempted only when:

manifest.latestVersion > localVersion

Database versioning is independent of the Android application's versionCode.

Safe installation

A candidate database is first downloaded to a temporary file:

download_<manifest.fileName>

The temporary file is parsed before installation.

The updater requires:

downloadedDatabase.versionCode == manifest.latestVersion

Only after successful parsing and version validation does it replace/install the final file.

This protects the current working database from an invalid candidate download.

Failure handling

Remote update errors are caught and logged. The updater intentionally continues and attempts to load the latest local database.

Thus, loss of connectivity or a failed remote update does not automatically prevent use of a previously installed valid database.

If local loading also fails, null is returned and the UI reports that the nuclide database is unavailable.

Network source

The v4.0 implementation constructs Google Drive direct-download URLs of the form used by its configured manifest and database file IDs.

The database host is therefore an implementation detail of v4.0, not part of NDFS itself.

Updating the published database

A maintainer should:

  1. build and validate a new NDFS-compatible database;
  2. increment its database versionCode;
  3. package it as the expected JSON or ZIP;
  4. upload the package;
  5. update the manifest latestVersion, fileName and fileID;
  6. test update from a device holding the previous database version;
  7. test offline fallback after successful installation.
