TAlpha Nuclear Database

Specification

The formal schema is defined by the separately maintained TAlpha Nuclide Database Format Specification (NDFS). TAlpha v4.0 uses NDFS v3.0: the v1 core and v2 experimental fields are preserved, and adoptedLevels adds energetically accessible daughter-level candidates.

See Specifications.

Kotlin data model

NuclideDatabase.kt defines:

NuclideDatabase
 ├─ versionCode
 ├─ formatVersion
 └─ layers[]

NuclideLayer
 ├─ a
 └─ nuclides[]

NuclideRecord
 ├─ a
 ├─ z
 ├─ symbol
 ├─ massExcess
 ├─ qAlpha
 ├─ estimated
 ├─ tHalfExpYears
 ├─ alphaDecayJson
 └─ rawJson

Parsed JSON fields

The Android parser requires the v1 core:

versionCode
layers
layers[].A
layers[].nuclides
Z
symbol
massExcess
qAlpha
estimated

It additionally reads:

formatVersion
T_hl_exp
alphaDecay
adoptedLevels (retained inside rawJson and parsed by AlphaDecayScheme.kt)

T_hl_exp is accepted only when it is finite and greater than zero.

The complete original nuclide JSON object is retained as rawJson. This allows AlphaDecayScheme.kt to read NDFS v3.0 adoptedLevels without expanding the public NuclideRecord data class.

NDFS v3.0 candidate levels

Each adoptedLevels[] item may include an ENSDF level identifier, dataset information, excitation energy, spin/parity, derived qAlphaLevel_keV and l_min. The database-generation pipeline keeps only energetically accessible levels according to its source-selection policy.

adoptedLevels and alphaDecay.transitions are intentionally different:

  • adoptedLevels describes potential daughter final states;
  • alphaDecay.transitions preserves experimentally observed/evaluated transitions.

JSON and ZIP support

The local loader accepts files named as versioned TAlpha databases and supports:

talpha_nuclides_<version>.json
talpha_nuclides_<version>.zip

For a ZIP package, the loader scans entries until it finds a non-directory .json entry and parses that content.

Local storage

The database directory is:

filesDir/nuclide_database/

The application determines the latest local database by extracting the numeric version from matching JSON/ZIP filenames and selecting the greatest version.

Basic parser validation

After parsing, the Android code requires:

versionCode > 0
layers is not empty

The updater additionally verifies that a newly downloaded database's internal versionCode equals the manifest's latestVersion.

The formal NDFS document defines the broader schema and physical-consistency rules; this page only describes checks implemented by the Android reader.

Compatibility

formatVersion is optional in the Android data model. Optional v2/v3 fields may be absent. This permits the reader to retain compatibility with records that only contain the earlier core fields, provided the required parser fields are present.
