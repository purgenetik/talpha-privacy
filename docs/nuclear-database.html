TAlpha Nuclear Database

Specification

The formal schema is defined by the separately maintained TAlpha Nuclide Database Format Specification (NDFS). TAlpha v5.3 uses NDFS v3.0: the v1 core and v2 experimental fields are preserved, and adoptedLevels adds energetically accessible daughter-level candidates. Version 5.3 changes the Android storage/loading mechanism, not the NDFS interchange schema.

See Specifications.

NuclideDatabase
 ├─ versionCode
 ├─ formatVersion
 └─ layers[]

NuclideLayer
 ├─ a
 └─ nuclides[]

NuclideRecord
 ├─ a
 ├─ z
 ├─ symbol
 ├─ massExcess
 ├─ qAlpha
 ├─ estimated
 ├─ tHalfExpYears
 ├─ alphaDecayJson

NuclideDatabaseInfo

Parsed JSON fields

The Android parser requires the v1 core:

versionCode
layers
layers[].A
layers[].nuclides
Z
symbol
massExcess
qAlpha
estimated

It additionally reads:

formatVersion
T_hl_exp
alphaDecay
adoptedLevels (serialized as adoptedLevelsJson for AlphaDecayScheme.kt)

T_hl_exp is accepted only when it is finite and greater than zero.

Only the two nested structures needed by the scheme renderer are retained as compact JSON strings (alphaDecayJson and adoptedLevelsJson). The complete database root is not retained in memory.

NDFS v3.0 candidate levels

Each adoptedLevels[] item may include an ENSDF level identifier, dataset information, excitation energy, spin/parity, derived qAlphaLevel_keV and l_min. The database-generation pipeline keeps only energetically accessible levels according to its source-selection policy.

adoptedLevels and alphaDecay.transitions are intentionally different:

  • adoptedLevels describes potential daughter final states;
  • alphaDecay.transitions preserves experimentally observed/evaluated transitions.

Interchange package and on-device layout

The published database remains a versioned JSON/ZIP package such as:

talpha_nuclides_<version>.zip

During installation, the loader scans the ZIP for a JSON entry and reads it with JsonReader. It copies one layers[] object at a time into a local layer file instead of constructing the complete JSON tree in memory.

Local storage

The database directory is:

filesDir/nuclide_database/

The v5.3 on-device structure is:

filesDir/nuclide_database/
└── DB_v<version>/
    ├── DB_v<version>_<A1>.json
    ├── DB_v<version>_<A2>.json
    └── ...

Each layer file contains one object with A and nuclides[]. Other installed database versions are preserved. A legacy JSON/ZIP can still be discovered as an offline compatibility source, but only a complete DB_vN directory counts as an installed layered version for update comparison.

On-demand loading

At startup the UI normally loads NuclideDatabaseInfo, not every NuclideRecord. NuclideSummary receives layerMassNumbers; when the user selects A, NuclideDatabaseViewModel.loadLayer(A) parses only DB_vN_A.json.

The ViewModel holds one selectedLayer. Before another layer is loaded, the previous reference is cleared and the earlier job is cancelled. This is the main v5.0/v5.3 memory optimization.

Basic parser validation

For a layered installation, the Android code requires:

versionCode == manifest expected version
formatVersion == 3.0
layers exists and is not empty
each A is positive and unique
each layer contains nuclides[]
every final DB_vN_A.json exists and is non-empty
the layer A matches its file name

Validation is performed in DB_vN_installing. The directory is renamed to DB_vN only after all layers pass validation. A failure removes the incomplete staging directory and leaves installed versions available.

The formal NDFS document defines the broader schema and physical-consistency rules; this page only describes checks implemented by the Android reader.

Compatibility

formatVersion is optional in the Android data model. Optional v2/v3 fields may be absent. This permits the reader to retain compatibility with records that only contain the earlier core fields, provided the required parser fields are present.
