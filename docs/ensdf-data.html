ENSDF Data in TAlpha v4.0

Role of ENSDF

Version 4.0 retains experimental alpha-decay information produced from ENSDF API data and adds energetically accessible adopted daughter levels used as potential alpha-decay candidates.

The Android application does not query ENSDF directly while the user browses the chart. It consumes the already prepared/normalized information stored in the downloaded TAlpha database.

This separates:

data acquisition / database generation

from:

mobile visualization / calculation

Data used by the Android application

For a nuclide, v4.0 can consume:

T_hl_exp
alphaDecay.decays
alphaDecay.transitions
adoptedLevels

The Android code uses these data to display:

  • evaluated parent alpha half-life when present;
  • daughter excited levels;
  • spin/parity when available;
  • transition intensity when available;
  • branch-specific Qα derived from parent Qα and daughter excitation energy;
  • potential final states with l_min when available; the Android renderer derives the branch Qα from the parent qAlpha and daughter excitation energy.

Provenance and normalization

The authoritative rules for ENSDF provenance, parent matching, dataset joins, adopted-level construction, archival records, units and conversion belong to TAlpha NDFS v3.0.

The Android reader assumes that database-generation scripts have already produced a validated normalized structure.

Experimental half-life

At nuclide level:

T_hl_exp

is read into:

NuclideRecord.tHalfExpYears

and can be displayed directly on the isobaric chart.

Inside a decay scheme, normalized decay records can provide:

halfLifeYears

which is associated with transitions through dataset IDs.

Important distinction

Four different kinds of information can coexist:

  1. evaluated experimental parent alpha half-life from the database;
  2. alpha-decay transition information from ENSDF-derived records;
  3. energetically accessible adopted daughter levels that represent potential, not necessarily observed, alpha branches;
  4. model half-life calculated by TAlpha from the selected A, Z, Qα, Eexc and l.

The application should preserve this distinction in UI and documentation.

Database-generation pipeline

NDFS v3.0 recommends a two-stage pipeline:

  1. download and archive complete ENSDF responses for reproducibility;
  2. deterministically merge the validated alpha data and energetically accessible adopted daughter levels into the compact production database.

The substantially revised database-generation notebook is maintained separately:

TAlpha database-generation notebook (Google Colab)

The Android application consumes the generated database and does not execute this production pipeline on the device.
